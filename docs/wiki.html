Async email sender

LinkedIn NL scraper

backend

  • Key file: backend/app/services/job_scraper.py — function scrape_linkedin_nl(query, location, limit)
  • Uses LinkedIn's public guest jobs API endpoint (no authentication or OAuth required) — the same endpoint LinkedIn's own job search pages hit before login
  • Returns up to 5 results per search (linkedin_limit = min(params.limit // 3, 5) in jobs.py)
  • Graceful 429 handling: if LinkedIn rate-limits the request the function logs a warning and returns an empty list rather than raising — the gather still collects results from Adzuna and Indeed
  • URL injection guard: only URLs whose path starts with /jobs/view/ are accepted. The canonical job URL is reconstructed from the path only (scheme + www.linkedin.com + path), discarding any query params or alternative hostnames from the API response
  • Wired into asyncio.gather() in backend/app/api/v1/jobs.py alongside the existing Adzuna and Indeed calls
Known limitation: LinkedIn blocks requests from cloud/data-center IPs (including Railway EU West) — they serve a bot-detection page with no job cards. The scraper returns [] gracefully. Code is correct; will work with a residential proxy post-beta.
Gotcha: LinkedIn's guest API is undocumented and may change without notice. The scraper is designed to fail silently — check job-count metrics if LinkedIn results stop appearing.
Security: URL reconstruction from path-only prevents a spoofed API response from injecting arbitrary URLs into the job pool.

URL-to-letter (POST /apply/from-url)

backendweb

  • Endpoint: POST /apply/from-url in backend/app/api/apply.py
  • Flow: fetch the job posting URL → extract title, company, description (via BeautifulSoup) → pass to Claude API → return motivation letter. Costs 1 credit.
  • SSRF protection (hardened in session 12): scheme must be http/https; netloc non-empty; hostname resolved to IP via socket.getaddrinfo; IP checked against private/loopback/link-local ranges; redirect-following disabled (allow_redirects=False); any 3xx redirect target is re-validated through the same SSRF checks before following
  • Credit debit is atomic: debit_one_credit Supabase RPC is called before the fetch — prevents double-spending in concurrent requests
  • writing_style field validated as a Literal type (_WritingStyle) — rejects any value not in the allowed enum, preventing prompt injection via that field
  • PromptInjectionError returns 422 and does not refund the credit (injection is user-caused, not a system failure)
  • Frontend: collapsible UI panel below the search bar in DashboardClient.tsx — text input for URL, Generate button, copy-to-clipboard on result
  • API client helper: apply.fromUrl in web/src/lib/api.ts
Gotcha: Some job boards (LinkedIn, Nationale Vacaturebank) require a logged-in session or have JS-rendered content — the scraper may return partial data. Claude still generates a letter but quality depends on how much text was extracted.

Security hardening — session 12

backend

  • SSRF HIGH x2 — /apply/from-url: (1) hostname resolved to IP via socket.getaddrinfo before request; private/loopback/link-local ranges rejected. (2) redirects disabled; each 3xx Location header re-validated through the same IP check before following. File: backend/app/api/apply.py
  • Route shadowing MEDIUM — FastAPI matched GET /jobs/{job_id} before GET /jobs/saved/list. Fixed by declaring /saved/list before /{job_id} in backend/app/api/jobs.py
  • Credit race condition MEDIUM — /apply/from-url previously fetched the page before debiting, allowing a race where two concurrent requests both passed the credit check. Fixed by calling debit_one_credit RPC atomically first; if the RPC fails (insufficient credits) the request aborts before any fetch or LLM call
  • Unbounded job_data MEDIUM — POST /jobs/saved accepted a bare dict for job_data, allowing arbitrarily large payloads. Replaced with SavedJobData Pydantic model with explicit field types and max-length constraints
  • writing_style injection MEDIUM — UrlLetterRequest.writing_style was a free str; replaced with _WritingStyle = Literal["professioneel", "enthousiast", "bondig", "creatief"] — Pydantic rejects anything else with a 422 before the field reaches the prompt
  • PromptInjectionError LOW — previously triggered a 500 and the credit had already been debited. Now returns 422; no refund (injection is a user input issue, not a system error)
  • Indeed href injection MEDIUM — scrape_indeed_nl extracted all <a href> values from Indeed HTML. A malicious Indeed page could inject arbitrary URLs. Fixed: only hrefs starting with /vacatures/, /rc/, /pagead/, or https://nl.indeed.com/ are accepted
Pattern: The atomic-debit-first pattern (RPC before external calls) should be applied to any future endpoint that consumes credits. Never check-then-debit in separate DB calls — always use the debit_one_credit RPC which is wrapped in a transaction.

Shared jobs pool (DB-first search)

backendsupabase

  • Architecture change: Jobs are no longer scraped per-user on every search. Instead, a shared jobs table is pre-populated; user searches query the DB first and only fall back to live scraping on a cache miss.
  • Removed: scraped_for_user column — all jobs in the pool are shared across users. DB migration drops the column and rebuilds indexes.
  • Full-text search: PostgreSQL tsvector column on the jobs table (to_tsvector('dutch', title || ' ' || description)) with a GIN index. search_jobs() queries this instead of scraping when results are fresh (<6 h old).
  • Cache TTL: 6 hours. If the newest matching row is older than 6 h, the endpoint falls back to live scraping and upserts results into the pool.
  • Stale cleanup: pg_cron scheduled job deletes rows older than 48 h daily — keeps the table small.
  • Prefetch cron: Admin endpoint POST /admin/prefetch-jobs is called daily at 06:00 (via cron-job.org). It runs 20 hardcoded popular NL job searches (e.g. "software developer Amsterdam", "verpleegkundige", "accountant") to warm the cache before peak hours.
  • Key files: backend/app/api/jobs.py, backend/app/services/job_scraper.py, DB migration dropping scraped_for_user + adding FTS index
Gotcha: The FTS tsvector uses the dutch dictionary — make sure all future job inserts also use 'dutch' in to_tsvector() or the GIN index will not match queries. English job titles may not stem correctly with the Dutch dictionary; consider 'simple' as a fallback if recall drops.
Gotcha: pg_cron must be enabled on the Supabase project (CREATE EXTENSION IF NOT EXISTS pg_cron in a migration). Supabase does not enable it by default on all plans — verify in the Extensions dashboard.

  • warn-cv-expiry — daily at 02:00 — warns users whose CV expires in 7 days
  • cleanup-expired-cvs — daily at 03:00 — deletes CVs past their retention date from Supabase Storage
  • follow-up reminder — Sundays at 09:00 — emails users with pending applications to follow up
  • job-digest — Mondays at 09:00 — sends weekly job digest to opted-in users
  • purge-inactive — monthly (1st of month) — deletes accounts inactive for 90+ days (after 30-day warning)
  • prefetch-jobs — daily at 06:00 — calls POST /admin/prefetch-jobs on the Railway backend; warms the shared jobs pool with 20 popular NL searches before peak hours. Authenticated with x-admin-key header.
  • daily-credits — daily at 06:00 Amsterdam time (Europe/Amsterdam) — calls POST /admin/cron/daily-credits on the Railway backend; grants +2 credits to all users with balance < 15. Protected by x-admin-key header. Idempotent — safe to re-run.

Invite security hardening

backend

  • Atomic redemption — use_invite_code(code TEXT) RPC in backend/supabase/migrations/010_invite_redeem_rpc.sql. The RPC checks use_count < max_uses and increments atomically; returns a boolean. Replaces the previous check-then-update that had a TOCTOU window.
  • Rate limits — slowapi decorators on all invite endpoints: 30/minute on /validate and /register; 5/minute on /admin/create. Keyed on client IP.
  • Silent exception swallow removed — the previous except Exception: pass block that ate errors is gone; exceptions now propagate to FastAPI's default error handler.
  • PII out of logs — email addresses and names are no longer written to log lines or stored in admin notes fields.
  • Invite code not in validate response — the raw invite code was previously echoed back; it is now omitted from the response body.
  • Waitlist TOCTOU fix — invite_waitlist_entry now uses an upsert (ON CONFLICT DO NOTHING) instead of a separate existence check + insert.
  • Empty key guard — _check_admin_key now explicitly rejects empty strings, preventing a blank x-admin-key header from matching if the env var is unset.
Pattern: Any future endpoint that checks a quota and then acts must do so atomically via an RPC — the same lesson as debit_one_credit. Never check-then-act in two separate DB round-trips.

Global IP rate limiter (FastAPI middleware)

backend

  • Key file: backend/app/main.py
  • Implemented as a Starlette BaseHTTPMiddleware — runs before any route handler.
  • Algorithm: sliding window — stores a collections.deque of timestamps per IP. On each request, old entries outside the 60-second window are pruned, then the current count is checked against the limit (200 req/60s).
  • Storage: in-process dict[str, deque] — no Redis dependency. Resets on dyno restart. Adequate for a single Railway instance; revisit if multiple replicas are added.
  • Memory bound: keys for IPs with no recent traffic are pruned on the next request from that IP — prevents unbounded growth under long-tail traffic.
  • OPTIONS requests are excluded — allows CORS preflight to pass through without counting against the limit.
  • Response on limit exceeded: HTTP 429 with Dutch message "Te veel verzoeken. Probeer het later opnieuw."
Gotcha: The in-process store means rate limit counters are not shared across multiple backend replicas. If Railway scales to more than one instance, move the store to Redis (e.g. redis-py + Railway Redis add-on) to enforce the limit cluster-wide.
Gotcha: IP-based limiting is defeated by proxies and shared NAT (e.g. corporate offices, mobile carriers). If abuse patterns emerge from a single forwarded IP block, consider adding a per-user-token layer on top of the IP limiter for authenticated endpoints.

Admin & apply hardening (PR #103)

backend

  • grant_credits RPC param fix — the RPC was being called with p_reference_id but the Supabase function signature expects p_reference. Corrected in backend/app/api/v1/admin.py and backend/app/api/v1/apply.py. Calls were silently failing (Supabase ignored the unknown parameter) without raising an error.
  • adjust_credits → grant_credits — several call sites referenced a non-existent adjust_credits RPC. Replaced with the correct grant_credits RPC throughout admin and apply modules.
  • CreditAdjust model hardening — reason field now has max_length=200 (was unbounded); delta is clamped to ±10,000 via Pydantic ge/le constraints. Prevents an admin from accidentally (or maliciously) granting an arbitrarily large credit amount via the API.
  • toggle_suspend existence check — the suspend endpoint now verifies the target user exists before attempting the write. Previously a missing user caused a 500; now returns a 404 with a clear message.
  • _fetch_job_page SSRF on every redirect hop — the SSRF IP-range check (blocks private/loopback/link-local addresses) was previously applied only to the initial URL. If the server returned a 3xx redirect, the redirect target was fetched without re-validation. Now every hop goes through the same socket.getaddrinfo + range-check pipeline. Key file: backend/app/api/v1/apply.py.
Pattern: SSRF protection must be applied on every HTTP hop, not just the first request. Attackers can chain redirects through a safe-looking URL to an internal endpoint. Always re-validate after following any 3xx response.
Pattern: When calling Supabase RPCs with keyword arguments, verify the param names match the SQL function signature exactly — Supabase silently ignores unknown kwargs instead of raising an error, which can mask broken call sites.
